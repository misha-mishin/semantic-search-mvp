# Семантический поиск товаров

Учебный MVP поиска карточек товаров по текстовому запросу для онлайн-каталога CalmFruits. Проект сравнивает лексический поиск на TF-IDF, семантический поиск на эмбеддингах и гибридное ранжирование. Результат поиска — упорядоченный список уникальных карточек `imt_id`.

Основная работа выполнена в `semantic_search_project.ipynb`: исследование данных, подготовка каталога, поисковые функции, эксперименты, оценка качества и выводы для бизнеса. Веб-приложение и отдельный API не реализованы.

```text
semantic-search-mvp/

```

Исходные данные, веса модели, кеши эмбеддингов, локальное хранилище MLflow и `.env` в репозиторий не включены.

## Данные

Данные загружаются из S3-совместимого хранилища Yandex Object Storage. Для выполнения тетради необходим доступ к учебному бакету; публичная ссылка для скачивания в репозитории не предоставляется.

| Файл | Назначение |
|---|---|
| `wb_products_raw_sample.parquet` | Исходный каталог из 200 000 строк |
| `wb_products_dedup.parquet` | Идентификаторы 4256 карточек пула оценки |
| `queries_synthetic_train.parquet` | Разработка и сравнение конфигураций: 700 запросов |
| `queries_synthetic_test.parquet` | Финальная оценка: 300 запросов |

Разметка содержит пары «запрос — товар» с релевантностью от 0 до 3. Ключ связи: `item_id` в разметке соответствует `imt_id` в каталоге.

Рабочий каталог ограничен одеждой и обувью. После дедупликации и удаления карточек без названия и описания остаётся 48 376 карточек. Тексты и признаки готовятся из исходного каталога; из `wb_products_dedup.parquet` используется только список идентификаторов.

## Поисковые подходы и эксперименты

- Лексический поиск: TF-IDF, униграммы и биграммы, `min_df=3`, `max_features=30000`.
- Семантический поиск: `intfloat/multilingual-e5-small`, нормализованные эмбеддинги размерности 384, лимит 256 токенов, префиксы `query: ` и `passage: `. Используется точный поиск без ANN-индекса.
- Гибрид: Reciprocal Rank Fusion с `rank_constant=60` и глубиной выдачи каждого компонента `candidate_k=100`.

Проверены три гипотезы:

1. Добавление `brand_name` в текст карточки улучшило лексический и семантический поиск на train.
2. Исключение `description` не улучшило основную метрику; описание сохранено.
3. RRF показал лучший NDCG@10 на train, но его преимущество над самостоятельной семантикой не сохранилось на test.

Итоговый полный шаблон текста: название, предметная категория, бренд, цвета и описание (`full_brand`). Исходный baseline использует те же поля без отдельного бренда (`full_no_brand`).

## Протокол оценки и результаты

Разработка и выбор конфигураций выполняются на фиксированном наборе из 700 train-запросов. Финальное сравнение — на 300 test-запросах. Поиск при основной оценке ограничивается пулом из 4256 карточек до выбора top-K; TF-IDF и эмбеддинги строятся по всему подготовленному каталогу.

- Основная метрика выбора: NDCG@10.
- Дополнительные: Recall@10, Precision@5, MRR@10 и HitRate@10.
- Значения K: 1, 3, 5, 10.
- Для бинарных метрик релевантность определяется как `relevance >= 2`.
- NDCG использует градуированные оценки и `gain = 2^relevance - 1`.
- Товар без оценки для конкретного запроса получает релевантность 0.
- Метрики усредняются по запросам.

### Финальные результаты на test

| Конфигурация | NDCG@10 | Recall@10 | Precision@5 | MRR@10 | HitRate@10 |
|---|---:|---:|---:|---:|---:|
| TF-IDF · full_no_brand | 0.4134 | 0.3070 | 0.0780 | 0.1626 | 0.4200 |
| Semantic · full_no_brand | 0.5118 | 0.6578 | 0.2220 | 0.5338 | 0.7767 |
| Semantic · full_brand | 0.5906 | 0.8188 | 0.2647 | 0.6816 | 0.9167 |
| Hybrid RRF · full_brand | 0.5707 | 0.7266 | 0.2260 | 0.5215 | 0.8100 |

До финальной оценки по NDCG@10 на train выбран гибрид: 0.6007 против 0.5874 у семантического `full_brand`. На test лучшие наблюдаемые значения всех пяти показателей получил семантический `full_brand`, заранее включённый в сравнение. После просмотра test параметры не донастраивались.

Полные финальные метрики и идентификаторы runs находятся в `results/final_test/final_test_summary.csv`. Подробные результаты экспериментов и анализ ошибок — в тетради и workbook.

## Установка

Окружение автора: Python 3.13.5, macOS с использованием MPS. Код автоматически выбирает CUDA, MPS или CPU в зависимости от доступности. Возможность установки на другом оборудовании зависит в том числе от поддержки закреплённых версий PyTorch.

```bash
git clone https://github.com/misha-mishin/semantic-search-mvp.git
cd semantic-search-mvp
python3.13 -m venv .venv
```

Активируйте окружение:

```bash
# macOS / Linux
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

Установите зависимости и зарегистрируйте ядро:

```bash
python -m pip install -r requirements.txt
python -m pip check
python -m ipykernel install --user --name semantic-search-mvp --display-name "Python (semantic-search-mvp)"
```

При первой загрузке модели требуется доступ к Hugging Face. Эмбеддинги рассчитываются при отсутствии соответствующего локального кеша; первый запуск поэтому занимает больше времени.

## Настройка доступа

Скопируйте `.env.example` в `.env` в корне репозитория:

```bash
# macOS / Linux
cp .env.example .env

# Windows PowerShell
Copy-Item .env.example .env
```

Заполните в `.env` переменные `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`
и `S3_BUCKET` для доступа к данным, а также `MLFLOW_TRACKING_URI`,
`MLFLOW_TRACKING_USERNAME` и `MLFLOW_TRACKING_PASSWORD`
для подключения к удалённому серверу MLflow.

Тетрадь использует S3 endpoint `https://storage.yandexcloud.net` и имена файлов, перечисленные в разделе «Данные». Файлы должны быть доступны по этим ключам в указанном бакете. Не публикуйте `.env` и секреты в Git.

При отсутствии настроек удалённого MLflow или ошибке подключения тетрадь переключается на локальное хранилище `.mlflow/` с SQLite. Фактический режим выводится при подключении. Локальные runs автоматически на удалённый сервер не переносятся; для проверки учебного сервера убедитесь, что выбран режим `remote`.

## Запуск тетради

Запускайте из корня репозитория: относительные пути к `check_mlflow.py`, кешам и результатам рассчитаны на эту рабочую директорию.

Откройте `semantic_search_project.ipynb` в VS Code с поддержкой Jupyter либо в установленном Jupyter-интерфейсе, выберите ядро `Python (semantic-search-mvp)` и выполните ячейки последовательно с начала.

Для выполнения без графического интерфейса:

```bash
python -m nbconvert --to notebook --execute --inplace semantic_search_project.ipynb --ExecutePreprocessor.kernel_name=semantic-search-mvp --ExecutePreprocessor.timeout=-1
```

Команда обновляет outputs исходной тетради. Полный запуск повторно оценивает train-конфигурации и создаёт соответствующие MLflow runs.

### Сохранённая финальная оценка

Блок финального теста загружает существующие JSON из `results/final_test/`, не выполняя поиск заново для этих конфигураций. Если результата нет, текущий код выполняет оценку и сохраняет новый результат вместе с run ID. Manifest проверяет совпадение тестовых данных, K и порога, но не является полной проверкой идентичности конфигураций.

Для просмотра готовых результатов удалять файлы не нужно. Кеш относится к зафиксированным конфигурациям; его нельзя использовать как результаты изменённой модели. Текущий test не следует применять для дальнейшей настройки и повторного выбора параметров.

## MLflow

Название эксперимента: `wb-semantic-search`. Логируются параметры, метрики и артефакты оценки: `config.json`, `per_query_metrics.csv`, `summary_metrics.csv`, `rankings.csv` и `golden.csv`.

Проверка удалённого эксперимента из корня репозитория:

```bash
python check_mlflow.py wb-semantic-search --env-file .env
```

Скрипт проверяет существование эксперимента, наличие успешных runs и обязательных параметров и метрик. Эта проверка не заменяет проверку содержимого артефактов. Для локального режима используется вызов проверки из тетради, передающий фактически выбранный tracking URI.

## Ограничения и вывод для бизнеса

- Запросы синтетические, а разметка неполная: потенциально подходящие неразмеченные товары получают оценку 0.
- Метрики пула не являются оценкой поиска по всему каталогу. Выводы ограничены одеждой и обувью.
- Train используется для разработки без отдельной валидационной части. Test ранее просматривался при EDA и проверках целостности, но не использовался для настройки по метрикам поиска.
- Статистическая значимость различий, нагрузочная устойчивость и бизнес-эффект не оценивались.
- Соответствие бренду, цвету и категории не гарантируется одним текстовым сходством. Польза на опечатках и разговорных запросах отдельно не измерялась.

Рекомендуется проверять семантический `full_brand` в ограниченном пилоте, а не сразу заменять действующий поиск. Следующие шаги: реальные запросы и дополнительная разметка, новый независимый тест, проверка атрибутных ограничений и производительности, затем контролируемый пилот.
