# Проект: семантический поиск товаров по текстовому запросу (query-to-item)

## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла. Три из них — рабочие, к ним вы будете обращаться постоянно, один — служебный, нужен для одного этапа проекта.

**Итоговые артефакты проекта:**

- Jupyter-тетрадь с EDA, пайплайном и оценкой качества системы;
- эксперименты, логируемые в MLflow;
- этот документ, заполненный по ходу работы;
- дополнительная часть проекта — Streamlit-приложение.

## 2. План базового пайплайна

**2.1. Формулировка задачи своими словами**

Нужно по короткому текстовому запросу найти в каталоге CalmFruits подходящие карточки товаров (`imt_id`) и выстроить их в порядке релевантности. Данные - каталог товаров (200 тыс. строк, из них для работы взят подкаталог «Одежда» и «Обувь») и синтетическая разметка «запрос - товар» с оценкой релевантности 0–3. Качество измеряем по golden-сету из 700 train-запросов метриками Precision/Recall/Hit Rate/MRR@K и NDCG@K (K = 1, 3, 5, 10). Бизнесу это нужно, чтобы понять, стоит ли заменять или дополнять поиск по ключевым словам векторным.

**2.2. Подготовка данных** 

- Отобрал категории «Одежда» и «Обувь» - именно они есть в обучающей разметке: 56 503 строки.
- Дедуплицировал по `imt_id`: из вариантов карточки оставлял строку с самым длинным описанием. Цвета (`nm_colors_names`) собрал по всем вариантам карточки (топ-5 самых частых). Получилось 48 489 уникальных карточек.
- Отсеял карточки, у которых одновременно пусты `imt_name` и `description`: удалено 113, осталось 48 376 (0.2%). Это не критично, но отметим как показатель качества каталога.
- Очистил текст (функция `clean_text`): HTML-сущности и теги, ссылки, лишние пробелы и пунктуация, нижний регистр. Та же функция применяется и к запросам.
- Собрал `product_text` как `imt_name . subj_name . description . nm_colors_names` с разделителем « . »; пустые поля пропускаются, строк «nan»/«None» нет. Бренд не включён по договорённости на QA-сессии, но в названиях и описании он встречается. Проверил вручную на 15 карточках.

**2.3. Лексический поиск (baseline)**

- TF-IDF по `product_text`, `ngram_range=(1, 2)`.
- Без ограничений словарь с биграммами - ~296 тыс. признаков, половина терминов встречается в одном документе. Поэтому поставил `max_features=10 000` и `min_df=3`.
- Реализована `search_lexical(query, top_k)`: очистка запроса, косинусное сходство, топ-K по убыванию.
- Проверил на 3 случайных запросах: лексика находит карточки с буквальными совпадениями слов (например, для «bmw mms» - товары с этими токенами в названии).

**2.4. Семантический поиск**

- Модель `intfloat/multilingual-e5-small` (поддерживает русский, 384-мерные векторы, компактная для MVP).
- Префиксы `query:` / `passage:` по рекомендации модели. Тексты кодируются батчами по 64, векторы L2-нормализованы, поэтому косинус считается матричным умножением. Эмбеддинги сохранены в `.npy`.
- `max_seq_length = 256` токенов. По выборке 3000 карточек p95 ≈ 247, p99 ≈ 430 токенов; обрезается ~4.5% текстов. Это осознанный компромисс по скорости.
- Реализована `search_semantic(query, top_k)` с тем же интерфейсом, что и лексическая. Индекс - полный перебор: на ~48 тыс. карточек этого достаточно.
- На тех же 3 запросах семантика возвращает более «широкую» выдачу, а лексика - точные совпадения слов. Это ручная проверка, не метрика.

**2.5. Оценка качества** 

- Golden-сет: 700 запросов из `queries_synthetic_train`, все размеченные товары есть в каталоге; формат - словарь `query_id → {query_text, rels: {imt_id: relevance}}`.
- Порог бинаризации `RELEVANCE_THRESHOLD = 2` (оценки 2 и 3 - релевантно), вынесен в параметр. K = 1, 3, 5, 10.
- Precision@K, Recall@K, Hit@K и MRR@10 считаются по бинарной релевантности; NDCG@K - по полной шкале 0–3 с gain = 2^rel − 1.
- Поиск - по всему каталогу (~48 тыс.). Товар вне разметки = нерелевантный.
- Потолки Precision@K, обусловленные разметкой (в среднем 2.57 релевантных на запрос): @1 = 1.0, @3 = 0.607, @5 = 0.441, @10 = 0.252.
- Время прогона 700 запросов: лексика ~3 с, семантика ~14 с. Сводная таблица сохранена в `metrics_week2.csv`.

**2.6. Результаты базового сравнения**

Порог релевантности ≥ 2, K = 1/3/5/10, 700 запросов.

| Метрика | Lexical | Semantic |
|---|---|---|
| Precision@1 (=Hit@1) | 0.0114 | 0.1343 |
| Precision@3 | 0.0110 | 0.1000 |
| Precision@5 | 0.0086 | 0.0786 |
| Precision@10 | 0.0084 | 0.0604 |
| Recall@1 | 0.0051 | 0.0877 |
| Recall@3 | 0.0145 | 0.1687 |
| Recall@5 | 0.0164 | 0.2151 |
| Recall@10 | 0.0286 | 0.2976 |
| Hit@3 | 0.0329 | 0.2571 |
| Hit@5 | 0.0386 | 0.3243 |
| Hit@10 | 0.0600 | 0.4386 |
| NDCG@1 | 0.0208 | 0.1137 |
| NDCG@3 | 0.0315 | 0.1475 |
| NDCG@5 | 0.0356 | 0.1545 |
| NDCG@10 | 0.0419 | 0.1635 |
| MRR@10 | 0.0243 | 0.2199 |

**Сравнение подходов.** Семантика лучше по всем метрикам при любом K: NDCG@10 выше в ~3.9 раза, Recall@10 - в ~10, MRR - в ~9. Лексика практически не находит нужные товары (Hit@10 = 6%): запросы короткие и лексически не совпадают с карточками, так что буквальные совпадения слов почти не попадают в разметку.

**Главные наблюдения.**
- Лидера по K менять не приходится: семантика впереди и на K = 1, и на K = 10. Её метрики растут с K, то есть часть релевантных товаров стоит в позициях 2-10.
- Hit@10 = 0.44 при Recall@10 = 0.30: для 44% запросов найдено хоть что-то релевантное, но для ~56% в топ-10 нет ничего. В абсолютных значениях этого пока мало для продакшена.
- NDCG@1 (0.114) ниже Precision@1 (0.134): на первом месте часто стоит товар с оценкой 2, а не 3. Бинарные метрики этого не видят.
- Низкий Precision@10 = 0.06 в основном следствие разметки (потолок 0.252). Ориентируемся на NDCG@10, Recall@10, MRR и Hit@10.
- Значений, близких к 1, нет, поэтому подозрений на тривиальность задачи (совпадение запроса и карточки) нет.

**Примеры расхождений.** 
- Лексика сильна на запросах вида «категория + конкретная деталь» («на молнии», «с капюшоном», «с перфорацией», «на бретелях», «с меховой подкладкой»). Такие признаки встречаются в описаниях буквально, и TF-IDF их находит. Эмбеддинг «размывает» мелкую деталь общим смыслом карточки.
- Семантика выигрывает на запросах с несколькими прилагательными или общей характеристикой («нарядные», «шелковые… домашние», «желтые длинные хлопковые»), где слова запроса и карточки не совпадают буквально, но смысл близок.
- Опечатка в «килты банные копмлет» ломает лексический поиск (токен не найдётся), а эмбеддинг к ней устойчив.
- Бренд сам по себе победителя не определяет: он встречается в обоих списках. Возможное объяснение для «куртки bmw mms»: лексика вытаскивает любые товары бренда (по токену), а семантика учитывает ещё и категорию «куртки».
- Подходы дополняют друг друга: лексика - точные признаки, семантика - смысл и устойчивость к формулировкам и опечаткам. Это основание для гибридного поиска на неделе 3.

**Итог первой итерации:** семантика — более перспективная основа для улучшений, но текущих результатов недостаточно для решения о внедрении. TF-IDF сохраняем как baseline и компонент для проверки гибридного поиска.


**2.7. Риски и открытые вопросы по итогам недели**

- Неразмеченные, но подходящие товары считаются нерелевантными, поэтому метрики могут быть занижены, особенно для общих запросов.
- Разметка синтетическая: на реальных запросах пользователей качество может отличаться.
- Golden-сет небольшой (700 запросов, в среднем 2.57 релевантных): метрики посчитаны один раз, без доверительных интервалов. Для сравнения близких вариантов потребуется bootstrap.
- Бренд исключён из `product_text` по решению заказчика; для запросов-брендов это может снижать качество, проверить влияние можно в экспериментах недели 3.
- Обрезка до 256 токенов затрагивает ~4.5% карточек; влияние на метрики не измерено.
- Минимальные планки метрик заказчик не задал: решение о достаточности качества пока открыто.
- Оценка сделана только на train-golden; тест не использован и оставлен для финальной проверки.
- Каталог ограничен двумя категориями; на остальной каталог выводы не распространяются без повторной проверки.
