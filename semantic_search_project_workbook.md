# Проект: семантический поиск товаров по текстовому запросу (query-to-item)

## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла. Три из них — рабочие, к ним вы будете обращаться постоянно, один — служебный, нужен для одного этапа проекта.

**Итоговые артефакты проекта:**

- Jupyter-тетрадь с EDA, пайплайном и оценкой качества системы;
- эксперименты, логируемые в MLflow;
- этот документ, заполненный по ходу работы;
- дополнительная часть проекта — Streamlit-приложение.

## 2. План базового пайплайна

**2.1. Формулировка задачи своими словами**

Нужно по короткому текстовому запросу найти в каталоге CalmFruits подходящие карточки товаров (`imt_id`) и выстроить их в порядке релевантности. Данные - каталог товаров (200 тыс. строк, из них для работы взят подкаталог «Одежда» и «Обувь») и синтетическая разметка «запрос - товар» с оценкой релевантности 0–3. Качество измеряем по golden-сету из 700 train-запросов метриками Precision/Recall/Hit Rate/MRR@K и NDCG@K (K = 1, 3, 5, 10). Основной расчёт ведётся по каталогу оценки (`wb_products_dedup`, 4256 карточек), для сравнения те же запросы прогнаны по полному подготовленному каталогу (48 376 карточек). Бизнесу это нужно, чтобы понять, стоит ли заменять или дополнять поиск по ключевым словам векторным.

**2.2. Подготовка данных** 

- Отобрал категории «Одежда» и «Обувь» - именно они есть в обучающей разметке: 56 503 строки.
- Дедуплицировал по `imt_id`: из вариантов карточки оставлял строку с самым длинным описанием. Цвета (`nm_colors_names`) собрал по всем вариантам карточки (топ-5 самых частых). Получилось 48 489 уникальных карточек.
- Отсеял карточки, у которых одновременно пусты `imt_name` и `description`: удалено 113, осталось 48 376 (0.2%). Это не критично, но отметим как показатель качества каталога.
- Очистил текст (функция `clean_text`): HTML-сущности и теги, ссылки, лишние пробелы и пунктуация, нижний регистр. Та же функция применяется и к запросам.
- Собрал `product_text` как `imt_name . subj_name . description . nm_colors_names` с разделителем « . »; пустые поля пропускаются, строк «nan»/«None» нет. Бренд не включён по договорённости на QA-сессии, но в названиях и описании он встречается. Проверил вручную на 15 карточках.
- Каталог оценки: загрузил `wb_products_dedup.parquet` и взял из него только список `imt_id` (4256 карточек). Все они входят в подготовленный каталог (3381 «Одежда», 875 «Обувь»), все 11 453 размеченные пары golden-сета лежат внутри этого пула. Тексты и признаки берутся из собственного каталога. Пул применяется как маска при ранжировании, индексы (TF-IDF и эмбеддинги) построены по всем 48 376 карточкам.

**2.3. Лексический поиск (baseline)**

- TF-IDF по `product_text`, `ngram_range=(1, 2)`.
- Без ограничений словарь с биграммами - ~296 тыс. признаков, половина терминов встречается в одном документе. Поэтому поставил `max_features=10 000` и `min_df=3`.
- Реализована `search_lexical(query, top_k)`: очистка запроса, косинусное сходство, топ-K по убыванию. Функция создаётся фабрикой с необязательной маской: `search_lexical_base` ищет по всему каталогу, `search_lexical` - только по каталогу оценки.
- Проверил на 3 случайных запросах (полный каталог). Лексика цепляется за редкие токены: для «пуховики bmw mms» нужный пуховик стоит лишь на 4-м месте после кроссовок и курток бренда, для «трикотажные водолазки» в выдаче есть «комплект» и детские брюки, совпавшие по отдельным словам.

**2.4. Семантический поиск**

- Модель `intfloat/multilingual-e5-small` (поддерживает русский, 384-мерные векторы, компактная для MVP).
- Префиксы `query:` / `passage:` по рекомендации модели. Тексты кодируются батчами по 64, векторы L2-нормализованы, поэтому косинус считается матричным умножением. Эмбеддинги сохранены в `.npy`.
- `max_seq_length = 256` токенов. По выборке 3000 карточек p95 ≈ 247, p99 ≈ 430 токенов; обрезается ~4.5% текстов. Это осознанный компромисс по скорости.
- Реализована `search_semantic(query, top_k)` с тем же интерфейсом, что и лексическая, и такой же маской (`search_semantic_base` - полный каталог, `search_semantic` - каталог оценки). Индекс - полный перебор: на ~48 тыс. карточек этого достаточно.
- На тех же 3 запросах семантика ставит «Пуховик BMW MMS» на 1-е место, а для «трикотажные водолазки» возвращает только водолазки. Но для «шубы искусственные с капюшоном» после первой карточки идут «Шубы натуральные»: эмбеддинг плохо различает противоположные атрибуты. Это ручная проверка, не метрика.

**2.5. Оценка качества** 

- Golden-сет: 700 запросов из `queries_synthetic_train`, все 11 453 размеченные пары входят в каталог оценки; формат - словарь `query_id → {query_text, rels: {imt_id: relevance}}`.
- Каталог оценки: пул `wb_products_dedup` (4256 карточек). Основной расчёт - по нему. Для справки те же запросы прогнаны по полному каталогу (48 376 карточек). Поиск всегда идёт по всему каталогу соответствующего набора, а не только по размеченным для запроса товарам.
- Порог бинаризации `RELEVANCE_THRESHOLD = 2` (оценки 2 и 3 - релевантно), вынесен в параметр. K = 1, 3, 5, 10.
- Precision@K, Recall@K, Hit@K и MRR@10 считаются по бинарной релевантности; NDCG@K - по полной шкале 0–3 с gain = 2^rel − 1.
- Товар вне разметки = нерелевантный.
- Потолки Precision@K, обусловленные разметкой (в среднем 2.57 релевантных на запрос, медиана 1): @1 = 1.0, @3 = 0.607, @5 = 0.441, @10 = 0.252.
- Время прогона 700 запросов: на пуле лексика 2.7 с, семантика 11.8 с; на полном каталоге 2.7 с и 13.7 с. Маска применяется после расчёта сходств, поэтому время почти не зависит от размера пула.
- Сводная таблица сохранена в `metrics_week2.csv` (строка на каждый движок и каталог, метаданные порога и K внутри файла).

**2.6. Результаты базового сравнения**

Порог релевантности ≥ 2, K = 1/3/5/10, 700 запросов. Основной вариант - каталог оценки (пул), для справки - полный каталог.

|---|---|---|---|---|
| Precision@1 (=Hit@1) | 0.0529 | 0.4014 | 0.0114 | 0.1343 |
| Precision@3 | 0.0748 | 0.2910 | 0.0110 | 0.1000 |
| Precision@5 | 0.0757 | 0.2314 | 0.0086 | 0.0786 |
| Precision@10 | 0.0744 | 0.1570 | 0.0084 | 0.0604 |
| Recall@1 | 0.0219 | 0.2352 | 0.0051 | 0.0877 |
| Recall@3 | 0.0821 | 0.4102 | 0.0145 | 0.1687 |
| Recall@5 | 0.1397 | 0.5031 | 0.0164 | 0.2151 |
| Recall@10 | 0.2836 | 0.6247 | 0.0286 | 0.2976 |
| Hit@3 | 0.1643 | 0.6057 | 0.0329 | 0.2571 |
| Hit@5 | 0.2357 | 0.6757 | 0.0386 | 0.3243 |
| Hit@10 | 0.4157 | 0.7571 | 0.0600 | 0.4386 |
| NDCG@1 | 0.1463 | 0.3502 | 0.0208 | 0.1137 |
| NDCG@3 | 0.2528 | 0.4512 | 0.0315 | 0.1475 |

**Сравнение подходов (пул).** Семантика лучше по всем метрикам при любом K. NDCG@10 выше в ~1.25 раза (0.498 против 0.400), Hit@10 - в ~1.8, Recall@10 - в ~2.2, MRR - в ~3.7. Разрыв сужается с ростом K: по NDCG@K он составляет ~2.4 раза при K = 1 и ~1.25 раза при K = 10, по Hit@K - ~7.6 и ~1.8 раза. Лексика находит релевантные товары, но ставит их ниже.

**Влияние каталога оценки.** При переходе от полного каталога к пулу NDCG@10 лексики вырос в ~9.5 раза (0.042 → 0.400), семантики - в ~3 раза (0.164 → 0.498). Полный каталог содержит ~44 тыс. карточек, которые асессоры не оценивали, и любой подходящий, но не размеченный товар засчитывается как ошибка. Поэтому основной расчёт ведём по пулу. Обратная сторона: пул (4256 карточек) намного меньше реального каталога, поэтому абсолютные значения на пуле - оценка сверху для реального поиска.

**Главные наблюдения (пул).**
- Hit@10 = 0.757 при Recall@10 = 0.625 у семантики: для 76% запросов в топ-10 есть хотя бы один релевантный товар. Без релевантных в топ-10 остаются 24% запросов у семантики и 58% у лексики.
- Потолок Precision@10 равен 0.252 из-за разметки. Семантика достигает ~62% потолка (0.157), лексика ~30% (0.074). Ориентируемся на NDCG@10, Recall@10, MRR и Hit@10.
- NDCG@1 семантики (0.350) ниже Precision@1 (0.401): на первом месте часто стоит товар с оценкой 2, а не 3. У лексики наоборот (NDCG@1 0.146, Precision@1 0.053): NDCG даёт частичный балл за оценку 1, а Precision при пороге 2 её не засчитывает.
- Значений, близких к 1, нет (максимум Hit@10 = 0.757), подозрений на тривиальность задачи нет.
- По суммарной метрике по всем K семантика лучше на 69.4% запросов, лексика на 29.9%, одинаково на 0.7%. Подходы дополняют друг друга.

**Примеры расхождений (пул).**
- Лексика лучше на запросах «категория + признак»: «худи с капюшоном», «толстовки на молнии», «женские шорты», «черные кожаные ботинки», «черные короткие болеро». Признаки встречаются в карточках буквально.
- Семантика лучше на формулировках, которые отличаются от карточки формой слов или составом: «джинсовые сарафаны», «джинсовые платья», «детские водолазки», «классические пальто», «фартуки детские с нарукавниками».
- Бренд победителя не определяет: он есть в обоих списках. Лексика лучше на «свитеры crespino», «ботильоны на каблуке ekonika», «слипоны на шнурках valen ki», «свитшоты kruzhok». Семантика лучше на «кроссовки cell pharos», «полуботинки gino rossi», «юбки на молнии youbka». Признак «на молнии» тоже встречается в обоих списках («толстовки на молнии» у лексики, «пуховики на молнии» и «кофты молнии» у семантики).
- Семантика путает противоположные атрибуты («шубы искусственные» / «шубы натуральные»); лексика реагирует на отдельные слова и цепляется за редкие токены («пуховики bmw mms»).

**Гипотезы для недели 3.**
1. Гибридный поиск (TF-IDF + эмбеддинги): лексика лучше на 29.9% запросов, и выигрывает там, где важна точная формулировка признака.
2. Лемматизация запроса и каталога для TF-IDF: словоформы («пуховики» / «пуховик», «джинсовые» / «джинсы») не склеиваются, что вероятно объясняет часть проигрышей лексики.
3. Влияние бренда в `product_text` (после согласования с заказчиком, так как бренд исключён по решению QA-сессии): бренд-запросы разделились между подходами.
4. Дообучение модели или реранкинг на train-разметке, чтобы различать противоположные атрибуты («искусственные» / «натуральные»).

**Итог первой итерации:** семантика - более перспективная основа, но выигрыш на пуле скромнее, чем показывала оценка на полном каталоге (NDCG@10 0.498 против 0.400, а не 0.164 против 0.042). Для решения о внедрении текущих результатов недостаточно. TF-IDF сохраняем как baseline и как компонент гибридного поиска.


**2.7. Риски и открытые вопросы по итогам недели**

- Неразмеченные, но подходящие товары считаются нерелевантными. На полном каталоге это сильно занижает метрики (NDCG@10 семантики 0.164 против 0.498 на пуле), поэтому основной расчёт ведётся по пулу оценки.
- Пул (4256 карточек) меньше реального каталога, поэтому значения на пуле - оценка сверху для реального поиска.
- Разметка синтетическая: на реальных запросах пользователей качество может отличаться.
- Golden-сет небольшой (700 запросов, в среднем 2.57 релевантных): метрики посчитаны один раз, без доверительных интервалов. Для сравнения близких вариантов потребуется bootstrap.
- TF-IDF и эмбеддинги построены по всему каталогу, пул применяется как маска при ранжировании. IDF поэтому считается по 48 376 документам, а не по пулу.
- Бренд исключён из `product_text` по решению заказчика; для запросов-брендов это может снижать качество, проверить влияние можно в экспериментах недели 3.
- Обрезка до 256 токенов затрагивает ~4.5% карточек; влияние на метрики не измерено.
- Минимальные планки метрик заказчик не задал: решение о достаточности качества пока открыто.
- Оценка сделана только на train-golden; тест не использован и оставлен для финальной проверки.
- Каталог ограничен двумя категориями; на остальной каталог выводы не распространяются без повторной проверки.
